# 媒资审核关键技术可行性验证

验证日期：2026-09-16

验证样本：仓库内 `examples/sample.mp4` 与 `examples/reference.jpeg`
验证环境：Apple Silicon macOS、本地 CPU；人脸原型使用项目 `transcrafteval` 环境，OCR 与 ASR 使用独立 `media-validation` 环境。

## 1. 结论

人物比对、画面 OCR、音轨 ASR、外挂字幕时间轴和多来源文本关联均已在真实样片上跑通。该技术路线适合后台异步审核：系统先完成分析和证据组织，再由审核员集中复核。

当前 CPU 基线不适合将 1080p 画面 OCR 作为逐帧实时能力。应采用字幕区域、固定采样间隔、连续重复结果聚合和后台队列。ASR 可作为高吞吐的全文本来源，但老片音质下存在错字，不能单独作为最终文字依据。

## 2. 样片媒体能力

| 项目 | 实测结果 |
|---|---|
| 容器与视频编码 | MP4，H.264 High，1920×1080，25 fps |
| 时长 | 120.13 秒（媒体容器）；OpenCV 按帧数计算为 120.04 秒 |
| 音轨 | AAC LC，48 kHz，立体声 |
| 解码能力 | OpenCV 可读取视频帧；随项目安装的 FFmpeg 运行时可识别视频和音轨 |

时间定位以媒体时间轴为准。帧数除以 FPS 与容器时长存在约 0.09 秒差异，播放器、OCR、ASR 与 SRT 应使用统一的秒级时间轴，并在界面中不宣称逐帧或逐字绝对精度。

## 3. 人物比对验证

使用 OpenCV YuNet 人脸检测与 SFace 特征比对，对 120 秒、1080p 样片逐帧检索指定参考人物。

| 指标 | 实测结果 |
|---|---|
| 处理时长 | 56.43 秒 |
| 处理速度 | 约 53.2 帧/秒，约 2.13 倍实时 |
| 候选片段 | 17 个 |
| 高相似度候选 | 7 个 |
| 关键帧人工抽查 | 候选覆盖正脸、侧脸、低照度画面；抽查关键帧与参考人物视觉一致 |

验证说明：单样片只能证明现有链路可解码、检测、比对、聚合和生成证据帧，不能证明跨演员、跨年代或不同片源的总体准确率。正式上线前需使用带人工标注的多片源测试集确定阈值、误报率和漏报率。

## 4. 画面 OCR 验证

使用 RapidOCR ONNX 在样片的烧录中文字幕上验证。样片 36.2 秒的字幕“您抽烟吧”在全帧和字幕区域均被识别。

| OCR 输入 | 识别结果 | 置信度 | 单帧耗时 |
|---|---|---:|---:|
| 1920×1080 全帧 | 您抽烟吧 | 0.979 | 0.274 秒 |
| 底部字幕区域 | 您抽烟吧 | 0.994 | 0.287 秒 |
| 放大两倍的字幕区域 | 您抽烟吧 | 0.995 | 0.209 秒 |

在 30–45 秒窗口中按 0.5 秒采样，共处理 31 帧，耗时 8.42 秒，提取到以下连续字幕组：

| 时间范围（秒） | OCR 文本 |
|---|---|
| 31.5–32.0 | 您坐 |
| 36.0–36.5 | 您抽烟吧 |
| 38.0–38.5 | 我抽旱烟 |
| 40.0–41.5 | 这个，我抽不惯 |
| 42.0–43.5 | 留着应酬客人吧 |

在字幕切换边缘出现了少量无意义识别结果，说明首期 OCR 需要：

1. 优先支持审核员选择字幕区域。
2. 使用固定采样间隔，默认从 0.5 秒开始标定。
3. 对相邻重复文本合并，并使用置信度、持续帧数和文本合法性过滤瞬时噪声。
4. 保留原始关键帧和文字框，不能将 OCR 结果直接作为最终业务文本。

按当前基线估算，120 秒样片以 0.5 秒采样进行字幕区域 OCR 约需 67 秒。该耗时适合后台分析，不适合逐帧实时扫描。

## 5. 音轨 ASR 验证

使用 faster-whisper `base` 模型、中文语言提示、CPU int8 推理和 4 线程，对完整样片音轨转写。

| 指标 | 实测结果 |
|---|---:|
| 音轨时长 | 120.13 秒 |
| 转写耗时 | 5.35 秒 |
| 推理速度 | 约 22.5 倍实时 |
| 输出分段数 | 45 段 |
| 语言识别 | 中文 |

30–45 秒窗口的关键结果如下：

| ASR 时间范围（秒） | ASR 文本 | 对照结论 |
|---|---|---|
| 35.93–36.97 | 您抽煙吧 | 与 OCR “您抽烟吧”一致，仅简繁不同 |
| 37.77–38.77 | 我出漢業 | 与 OCR “我抽旱烟”差异明显 |
| 39.77–41.65 | 這個我出不貫 | 与 OCR “这个，我抽不惯”部分一致 |
| 41.77–43.89 | 劉仗一如客人吧 | 与 OCR “留着应酬客人吧”差异明显 |

ASR 可作为高吞吐的全文检索和证据来源，但老片音质、口音和配乐会造成错字。文本规则应分别作用于 SRT、OCR 和 ASR；界面必须并列展示来源差异，人工确认后再形成问题。

## 6. SRT、文本标准化与自动关联

使用 SRT 解析器验证了 UTF-8 BOM、CRLF、中文字幕及统一时间偏移。解析后的原始文本可能保留换行空白，因此匹配和关联前必须进行空白规范化，同时保留原文用于证据回看。

简繁转换验证结果：

| 来源 | 原始文本 | 规范化文本 |
|---|---|---|
| OCR/SRT | 您抽烟吧 | 您抽烟吧 |
| ASR | 您抽煙吧 | 您抽烟吧 |

OCR 事件 36.0–36.5 秒与 ASR 段 35.93–36.97 秒时间重叠 0.57 秒，规范化文本完全一致，因此可以自动关联为同一复核事件。

自动关联应采用以下确定性条件：

- 同一个审核任务；
- 经 SRT 时间偏移校正后，时间重叠或处于可配置容差内；
- 简繁、空格和标点规范化后的文本及邻近上下文达到相似阈值；
- 同屏不同文字区域不能仅因时间重叠合并；相同关键词但不同位置或明显不同上下文保持独立。

“我抽旱烟”和 ASR 的“我出漢業”时间重叠但文本相似度仅 0.25，应保留为独立来源证据并提示差异，不能因时间接近自动合并。自动关联的目标是减少重复复核，不是隐藏来源冲突。

## 7. 推荐的运行边界

人脸、OCR 和 ASR 运行时包含不同的原生媒体库。实验中，在同一 Python 进程同时载入 OCR 的 OpenCV 与 ASR 的 PyAV 时，macOS 报告重复 FFmpeg 动态库。单独运行 OCR 与 ASR 进程时未出现该问题。

推荐使用独立的后台 worker：

| Worker | 职责 |
|---|---|
| 人脸 worker | 视频解码、人脸检测、特征比对和关键帧证据 |
| OCR worker | 帧采样、文字检测识别、文字框与重复文本聚合 |
| ASR worker | 音轨读取、转写、音频时间段与文本证据 |
| 任务服务 | 保存输入快照、调度 worker、汇总结果、自动关联和复核状态 |

Worker 可共享文件存储和任务数据库，但不应在一个解释器进程内混装所有推理运行时。项目的人脸原型继续使用仓库锁定的 `opencv-python-headless==4.13.0.92`；OCR 和 ASR 使用独立运行环境。

## 8. 首期技术基线

首期按异步任务设计。在当前 CPU 基线下，对 120 秒、1080p 样片顺序执行全帧人脸检索、0.5 秒采样 OCR 和 ASR，预计总处理时间约 129 秒；不同 worker 可按实际 CPU、内存和磁盘吞吐情况并行，但必须重新测量整体吞吐。

首期需要保留以下可配置项：人脸采样步长、OCR 采样间隔、OCR 区域、OCR 置信度过滤、文本连续合并间隔、SRT 时间偏移、自动关联时间容差、文本规范化规则和 ASR 模型/语言配置。

## 9. 上线前补充验证

在实现完整产品前，应建立独立于调参数据的人工标注集，至少覆盖：低清或黑白片源、字幕缺失、字幕位置变化、画面中的标牌文字、音质差、配乐干扰、多人对白、人物年龄变化、侧脸和小人脸。

验收时分别统计：

- 人物线索的误报、漏报和时间定位误差；
- OCR 的文字正确性、字幕事件召回和瞬时误识别；
- ASR 的规则词召回、文字错误和时间段误差；
- 自动关联的误合并、漏合并和人工拆分成本；
- 在相同审核范围与质量要求下，审核员完成审核、整理问题和生成修改清单的总用时。

只有在代表性片源上证明总人工时间下降，且关键问题不因自动关联、采样或模型错误被遗漏，才可将该能力作为首期审核流程的默认配置。

### 10.1 非真人“人脸”误检边界

旧片的图形画面进一步暴露了人物比对的关键风险。在 `One World or None` 的前 240 秒中按每秒抽样，YuNet 在 17 个样本中检出了“人脸”；人工查看后，这些样本均为重复出现的骷髅图形，并非真人。以该图形截图作为参考运行 185–225 秒片段检索，现有链路产生 3 个“confirmed”事件，最高相似度为 0.9606，单个事件支持帧数达到 186 帧。

这不是阈值问题，而是“人脸形状检测”与“真人身份检索”之间的语义缺口：高质量三维角色、骷髅、海报或画面中的头像都可能被检测和嵌入模型当作脸。提高相似度阈值不能消除同一非真人图像的稳定匹配，反而会降低真实老片人脸的召回。

因此首期应增加以下业务约束，而不是仓促引入一个未经验证的“动画过滤模型”：

1. 审核任务必须声明素材形态：真人、动画/图形、混合、未知。
2. “人物检索”仅接受明确对应真实人物的受控参考图；不得把从动画、海报或字幕画面截取的图像作为人物库样本。
3. 动画/图形任务默认不产生“真人命中”结论；混合或未知任务的命中只能进入人工复核，界面须显示原始证据帧。
4. 后续若要自动判断真人/动画，先在标注集上单独验证其召回和误拦截，再决定是否接入主链路；不应把它当作首期上线前置条件。

## 11. 更新后的可行性结论

补充样片覆盖了高清真人老片、黑白低清旧片、字幕和字卡、低码率图形、静音音轨、三维动画及真实外挂字幕。解码、OCR、ASR、SRT 和任务级证据组织仍然可行；其中 OCR 与 ASR 的性能结论在不同分辨率和音轨条件下保持成立。

人物检索的结论应收窄为：**它可作为已知真人的候选片段召回能力，不可独立形成“人物出现”的业务事实。** 首期以任务素材类型、受控人物参考图和人工复核约束误检，是比额外叠加通用图像分类模型更高 ROI 的方案。

## 12. 库驱动检测模式验证

本节验证的不是“让模型自行决定什么敏感”，而是：**审核对象均由检测库定义，模型只为某个库条目找候选证据。** 因尚未提供生产敏感库，以下条目是临时验证库，不应并入业务库或用于内容结论。

验证片源使用 [Date With Your Family, A (1950)](https://archive.org/details/DateWith1950)。该公开领域影片为 320×240、29.97 fps、约 10 分钟，包含多位真人、家庭餐桌画面和英语旁白；低分辨率和黑白画面接近旧片常见条件。

### 12.1 临时验证库

| 库类型 | 条目 ID | 条目定义 | 执行配置 |
|---|---|---|---|
| 人物库 | `person.test_actor_male_a` | 一名真实男性演员的受控参考图，取自 445 秒处的单人正脸画面 | YuNet + SFace；2 fps 采样；相似度阈值 0.65；至少 2 个支持帧 |
| 文字库 | `text.test_sensitive_gruesome_description` | 变体：`gruesome`、`unpleasant occurrences` | 规范化后的 ASR 文本子串匹配；保留原始 ASR 片段 |
| 内容库 | `content.test_group_dining_scene` | 同一画面内“至少 2 人 + 餐桌”的组合内容规则 | YOLO 通用目标召回；`person` ≥ 0.65 且 `dining table` ≥ 0.45；连续命中按时间聚合 |

这三种条目表达的是不同的业务结构：人物条目是受控特征样本，文字条目是规则和变体，内容条目是对基础视觉标签的组合规则。它们不应该被设计成同一种“关键词表”。

### 12.2 端到端实测结果

| 库条目 | 实际命中 | 原始证据 | 结论 |
|---|---|---|---|
| `person.test_actor_male_a` | 441.942–445.445 秒，最高相似度 0.8834，6 个支持帧 | 人脸关键帧 | 严格阈值下命中参考演员的近景，人物库 → 视频片段 → 证据帧的链路跑通。 |
| `text.test_sensitive_gruesome_description` | 434.51–441.03 秒命中 `gruesome`；441.03–443.27 秒命中 `unpleasant occurrences` | ASR 原文：`Discuss unpleasant topics such as gruesome sights or sounds.`、`Or unpleasant occurrences.` | 文字库 → ASR 分段 → 规范化变体匹配 → 原文证据的链路跑通。 |
| `content.test_group_dining_scene` | 433–440 秒连续命中 | 8 个 1 秒采样画面；每帧有 2–3 名 `person`，`dining table` 置信度为 0.450–0.528 | 内容库 → 基础对象召回 → 组合规则 → 时间窗口证据的链路跑通。 |

人物、文字和内容证据的时间段相邻或重叠，系统可以将它们归为同一“复核上下文”。但关联的语义必须受限：它可以说“人物命中发生在这段文字和场景附近”，**不能**仅凭时间接近就断言该人物说出了这句话，或该文字描述了画面中的人。说话人归属、行为归属需要独立模型或人工复核。

### 12.3 阈值必须属于库条目

以同一张参考图、同一段影片、2 fps 采样测试，原型的低门槛配置（确认阈值 0.34、单帧强命中阈值 0.45）产生 66 个候选、36 个自动确认。人工抽查其中的 0.523 分候选可见其为另一位女性演员，说明该配置不适合作为敏感人物库的自动确认门槛。

将人物条目阈值提升到 0.65 并要求至少两个支持帧后，只保留上述 441.942–445.445 秒的一个确认事件。这个实验不等于已完成准确率验收，但证明了一个关键设计原则：阈值、最小支持帧数、适用片源范围和确认策略必须随库条目版本保存，不能是全局固定参数。

### 12.4 性能与适用边界

在该 10 分钟、320×240 真人旧片上：

- 人物库检索（2 fps）用时 12.08 秒；
- 文字库所需的完整 ASR 用时 21.35 秒，输出 102 个分段；
- 内容库的 2 秒采样对象检测用时 11.61 秒，300 个样本中 291 个产生对象标签。

三条链路顺序运行约 45 秒，可作为后台审核任务并行调度。该内容检测器只覆盖通用对象类别；它验证了“基础标签 + 库规则”的机制，并不代表已经能可靠识别吸烟、武器使用、暴力行为、裸露或复杂剧情。此类生产内容条目必须分别具备可验证的底层检测能力（专用模型、视觉参考样本或后续多模态语义模型），否则库中即使有规则也不能产生可信命中。

## 13. 中国真人历史影片的库驱动验证

为验证库驱动方案在中国真人历史片上的适用性，补充使用了两个公开可获取的样本。它们仅用于本机技术验证；其中的人物、文字和内容条目均为临时测试库，不能直接视为生产审核规则或审核结论。

| 样片 | 测试片段与质量 | 用途 |
|---|---|---|
| [《中国人民的胜利》(1950)](https://commons.wikimedia.org/wiki/File:%E4%B8%AD%E5%9C%8B%E4%BA%BA%E6%B0%91%E7%9A%84%E5%8B%9D%E5%88%A9.webm) | 480p 转码，854×480；截取约 300–480 秒的 184 秒片段 | 历史人物、片内中文字幕、旗帜/人群/车辆及武器文字的多源证据 |
| [《上甘岭》(1956)](https://commons.wikimedia.org/wiki/File:%E4%B8%8A%E7%94%98%E5%B2%AD_1956.webm) | 480p 转码，624×480；验证前 330 秒中的 180–330 秒战场剧情 | 战斗语义、真人士兵画面、黑白旧片音画质量边界 |

Wikimedia Commons 的文件页分别标明前者为 1950 年中苏合拍纪录片、后者为 1956 年剧情片，并展示了相应的公开视频转码。选取它们不是为了对影片作价值判断，而是为了覆盖历史人物、政治性文字、战场和军用装备等需要由审核库定义的目标。

### 13.1 人物库：受控历史人物条目可以召回，但不可替代身份验收

在《**中国人民的胜利**》片段中建立临时人物条目 `person.test_historical_figure_a`：以约 98 秒处截取的一张单人清晰正脸作为受控参考图，对应画面中可人工识别的已故历史人物。该做法**只验证同片不同镜头下的检索链路**，不验证跨来源、跨年龄、跨画质的人物库准确率。

使用 YuNet + SFace、0.5 秒采样、候选阈值 0.45、确认阈值 0.55、单帧强确认阈值 0.65、至少 2 个支持帧，得到：

| 片段相对时间（秒） | 最佳相似度 | 支持帧 | 系统状态 |
|---|---:|---:|---|
| 15.0–18.0 | 0.6960 | 7 | 确认候选 |
| 30.0–33.0 | 0.6467 | 7 | 确认候选 |
| 35.5–36.0 | 0.5809 | 2 | 确认候选 |
| 96.5–101.0 | 0.9110 | 10 | 确认候选 |
| 150.5–151.5 | 0.6261 | 3 | 确认候选 |
| 162.5 | 0.4572 | 1 | 复核候选，不自动确认 |

人工抽查前五个证据帧，均为该历史人物在不同角度或不同景别中的画面；最后一个只有一个低分支持帧，正确地保留为复核而非自动确认。这个结果说明人物库条目可通过“阈值 + 连续支持帧 + 原始关键帧”压缩审核量；同时也说明库需要多张来自独立来源和不同姿态的经核验参考图，不能把从待审片中截出的单张图当作生产库的唯一依据。

### 13.2 文字库：OCR 是烧录中文字幕的主证据，ASR 用于补召回

对同一片段底部字幕区每 2 秒抽样，91 个样本中有 43 个非空 OCR 结果。OCR 准确识别出下列可由文字库定义的测试目标：

| 临时文字条目 | OCR 证据（片段相对秒） | ASR 对照 | 结论 |
|---|---|---|---|
| `text.test_historical_person_reference`：`毛主席`、`朱总司令`、`蒋介石` | 92–100 秒出现前两者；148–154 秒出现后两者 | 96.53–98.53 秒识别到“毛主席朱总司令”；其他位置存在漏字/错字 | 对于片内硬字幕，OCR 可作为高精度主证据。 |
| `text.test_weapon_equipment`：`自动步枪`、`大炮`、`装甲车`、`坦克` | 110–136 秒依次识别到四类词及其上下文 | ASR 将部分词转成“自动部枪”“打炮”等近音/错字 | ASR 应保留为独立的补召回来源，不能因时间接近自动改写或合并 OCR 原文。 |

因此，一个文字规则必须声明可接受的来源和各来源的确认策略。例如上述武器条目可设为：OCR 精确命中即可进入高置信文字证据；ASR 的近似命中只创建低置信候选，必须与 OCR、外挂字幕或人工复核相互印证。原文、标准化文本、库条目 ID 和时间范围应同时保存。

### 13.3 内容库：通用检测器可做粗召回，不能直接确认敏感内容

将 `content.test_military_equipment_context` 定义为临时组合条目：在 `text.test_weapon_equipment` 命中的窗口内，优先挑选存在多人、车辆或队列的画面，合并为一张审核卡，而不是将任一基础检测标签直接映射为“武器”或“暴力”。

实际运行中，YOLO11n 在 104–136 秒的多个画面稳定检出多人，并将部分车辆检为 `truck`、`car`；但也把旗帜/画面元素反复误识别为 `kite`、把装甲车误识别为 `bus`、`suitcase` 等。对《上甘岭》180–330 秒战场片段，它同样能检出真人士兵，却出现 `teddy bear` 等明显误报，且没有“步枪”“坦克”“暴力行为”等可直接使用的类别。

这次验证得到的正确处理结果是：

1. 《中国人民的胜利》110–136 秒生成一个“军用装备相关文字 + 真人/车辆画面”的**复核上下文**；证据中明确写出它来自 OCR 和通用对象检测，不能自动写成“已视觉确认武器”。
2. 《上甘岭》181.02–196.02 秒的 ASR 召回“敌人”“大规模进攻”“战斗十分激烈”等文本；与 208–240 秒的人物/战场画面可归入同一较大复核窗口，但不能仅由时间相邻推断台词描述了画面。
3. 对生产内容库，`武器`、`吸烟饮酒`、`暴力伤害`、`裸露/性暗示`、`标志/旗帜`、`特定场景或行为`必须分别配置实际可用的底层策略：专用检测模型、经验证的视觉检索样本、OCR/ASR/SRT 文字规则、或受约束的多模态模型。没有对应策略的库条目只能标为“暂不支持自动检测”，不能产生伪精确的结果。

### 13.4 多来源合并与过滤的最低规则

本次中国片源的结果说明，系统的核心不是把多个模型输出拼成一个分数，而是为审核员生成少而完整、可追溯的复核单元。首期建议采用下列确定性规则：

| 阶段 | 规则 | 产出 |
|---|---|---|
| 召回 | 任一库条目在其允许的来源上命中 | 不丢弃原始人物框、OCR 框、ASR 分段或对象框。 |
| 归并 | 同一任务、同一库条目或同一风险类；时间重叠或处于可配置窗口内；文本需满足规范化后相似条件 | 一个复核上下文，内部仍保留各来源独立证据。 |
| 过滤 | 低于条目阈值、只有孤立帧、OCR/ASR 冲突且无第二来源、或基础标签不支持目标语义 | 降为“待复核”或隐藏为噪声，不删除可追溯记录。 |
| 确认 | 只有当条目声明的确认条件全部满足，例如多参考人脸一致，或高质量 OCR 精确命中 | 可进入审核结论草稿；仍允许人工推翻。 |

后续接入 LLM 时，应把它放在“候选片段的受约束复核”这一环：输入库条目定义、少量关键帧和已提取的文字证据；要求返回结构化的“支持/不支持/不确定、可见证据、冲突和置信度”，且不得补造未见事实。LLM 输出不能绕过上表中的证据保存、阈值和人工最终确认。

## 14. 开源技术筛选与补充实测

本节不以 GitHub 热度作为选型依据，而是按本产品的四个实际问题筛选：能否提高中国旧片的敏感内容召回、能否减少无效推理、是否能保留可复核证据、以及本地部署与后续维护成本是否合理。测试均在 Apple Silicon macOS、本地 CPU 进行，模型加载时间不计入单片处理时间。

### 14.1 候选技术的取舍

| 技术/项目 | 适合解决的问题 | 当前判断 | 处理方式 |
|---|---|---|---|
| [PySceneDetect](https://github.com/Breakthrough/PySceneDetect) | 镜头边界、代表帧抽取、避免固定频率的冗余抽帧 | 高 ROI，适合首期接入 | 作为视频预处理 worker；按片源类型保存参数配置。 |
| [Chinese-CLIP](https://github.com/OFA-Sys/Chinese-CLIP) | 中文文本到画面的开放词表检索、视觉参考图检索 | 高价值的候选召回层，已在两部中国老片实测 | 作为内容库的“视觉语义策略”，只生成候选和关键帧，不自动确认风险。 |
| [Faiss](https://github.com/facebookresearch/faiss) | 人脸特征、关键帧视觉特征、参考样本的近邻检索 | 中期需要；小规模原型暂不必引入服务 | 当人物库/视觉样本库扩展到大量向量后接入，保留条目、向量版本与来源映射。 |
| [MMAction2](https://github.com/open-mmlab/mmaction2) | 时序动作识别、时空动作定位 | 有能力但首期 ROI 低 | 仅在某一类行为有足够标注样本、明确验收集和 GPU 预算后再做专项验证。通用 Kinetics/AVA 动作标签不等于广电审核语义。 |
| 通用 YOLO 目标检测 | 人、车等通用对象的粗线索 | 保留为辅助手段 | 不能用 COCO 标签直接确认武器、坦克、旗帜、暴力、吸烟等审核目标。 |
| NudeNet 等裸露检测器 | 裸露人体部位候选 | 需要单独合规与标注验证 | 不纳入当前原型。应先审查模型权重/许可证、适用地区和隐私要求，并在有权使用的标注集上评测。 |
| GitHub 敏感词审核 Demo | OCR/ASR/词库的流程参考 | 只参考数据流，不直接复用 | 缺少人物库、内容策略、证据合并、版本治理与审核闭环。 |

所有外部模型都必须在接入前单独核验代码许可证、模型权重许可证、下载来源和适用范围；代码仓库的开源许可证不自动覆盖模型权重或训练数据。

### 14.2 镜头切分实测：高 ROI，但参数必须随片源校准

使用 PySceneDetect 的 `ContentDetector` 对两部中国样本进行检测：

| 样片范围 | 参数 | 耗时 | 镜头数 | 相比 1 fps 固定抽帧的基础代表帧减少 |
|---|---|---:|---:|---:|
| 《中国人民的胜利》480p，184 秒 | `threshold=27`，最小镜头 0.5 秒 | 1.72 秒 | 40 | 约 78%（184 帧降至 40 帧） |
| 《上甘岭》180–330 秒，480p 黑白片 | `threshold=27`，最小镜头 2 秒 | 1.17 秒 | 14 | 约 91%（150 帧降至 14 帧） |

《上甘岭》若直接使用自适应检测的默认式参数，黑白颗粒、烟雾和老片亮度波动会形成 86 个过碎片段，反而增加推理量；设置最小镜头长度并采用内容阈值后恢复为 14 个可用片段。因此，镜头切分不能作为全局固定算法：任务需要保存 `detector`、阈值、最小镜头长度和片源类型，并允许审核员或运营配置“黑白旧片/现代高清/动画”的预设。

推荐使用方式不是“每个镜头只留一帧”，而是：每镜头先取代表帧；如果人物、OCR、ASR 或视觉语义命中，则对命中镜头和前后上下文加密抽帧。这同时保留召回率和处理效率。

### 14.3 中文开放词表视觉检索实测

安装并本地运行 Chinese-CLIP 的轻量 `RN50` 模型（模型文件约 308 MB），对镜头代表帧计算中文文本—图像特征。该模型是开放词表检索器：它不产生对象框，也不理解审核规则，只按文本描述对画面排序。

#### 《中国人民的胜利》

对 40 个代表帧提取特征用时 0.96 秒，约 42 帧/秒。人工查看排名靠前画面后得到：

| 中文查询 | 排名靠前的真实画面 | 结论 |
|---|---|---|
| `中华人民共和国国旗` | 5.05 秒为国旗近景；39.33 秒为广场旗帜与人群 | 可作为旗帜相关候选召回。 |
| `历史人物特写` | 98.70 秒为历史人物近景 | 可为人物库检索提供补充候选，但不能替代受控人脸比对。 |
| `军事阅兵队列` | 21.18 秒为乐队/阅兵队列 | 能召回军事仪式场景。 |
| `坦克或装甲车` | 128.07 秒为装甲车辆；132.67 秒为坦克画面 | 对车辆装备检索有效。 |
| `大炮` | 126.65 秒为牵引火炮画面 | 对明显装备画面有效。 |
| `群众集会` | 160.53 秒为人群近景 | 能用于人群场景候选。 |

#### 《上甘岭》

对 180–330 秒中 14 个镜头代表帧提取特征用时 0.33 秒。`爆炸和烟雾`的首位候选 201.67 秒为真实爆炸烟雾画面；`战场上的士兵`、`战斗场景`和`山地行军队伍`均将真人战场镜头排在前列；`手持步枪的士兵`的前列候选包含持枪士兵画面。

同时，`受伤的人`的首位候选 206.95 秒只是烟雾，真实伤员画面在 324.47 秒才成为后续候选。这是决定性的边界：**相似度排名可帮助不漏掉候选，但排名第一也不能构成“检测到伤员”或“确认暴力”的事实。**

### 14.4 建议接入形态

Chinese-CLIP 与人物、文字库的关系应如下：

1. 内容库条目可声明一组中文视觉查询、可选的正/负参考图、召回 Top-K 和最低相似度；例如 `content.weapon_context` 可配置“坦克、装甲车、牵引火炮、手持步枪的士兵”。
2. 对每个镜头代表帧计算视觉特征并保存；查询库条目时返回候选片段、相似度和关键帧，不写入确认结论。
3. OCR/ASR 命中武器、战斗等文字时，扩大同窗口的视觉 Top-K；视觉与文字相互支持时提升审核卡优先级，但仍保留各自独立证据。
4. 审核员确认或排除后，将关键帧与原因回流到条目评测集。积累足够标注后，才判断是否需要为某一类内容训练专用检测器或时序模型。

这条路线比一开始部署大而全的视频动作识别框架更适合当前阶段：镜头切分和中文语义检索已经在目标类型片源上证明能降低抽帧量、提升候选覆盖；专用模型和 LLM 则只应对已证明存在高价值、且通用检索不足的审核类别逐项引入。

## 15. 小型独立标注评测与多源归并验证

为避免只看“模型看起来命中”的演示效果，对两个片段按每 2 秒人工浏览一次画面，先记录可见目标的时间窗口，再以镜头代表帧上的中文查询检索结果计算目标窗口首次出现的排名。该集只有 12 个查询，且由当前验证样片人工标注，**不能**作为泛化准确率；它的用途是决定当前技术在产品中应处于“候选召回”还是“自动确认”的位置。

### 15.1 检索排名结果

| 样片 | 查询数量 | Hit@1 | Hit@3 | 关键误排 |
|---|---:|---:|---:|---|
| 《中国人民的胜利》 | 7 | 6/7 | 7/7 | `手持步枪的士兵`首位为阅兵乐队，真实持枪队列在第 3 位。 |
| 《上甘岭》 | 5 | 4/5 | 5/5 | `受伤的人`首位为烟雾，真实伤员在第 2 位。 |
| 合计 | 12 | 10/12 | 12/12 | 两个首位误排均涉及高语义、易混淆的审核目标。 |

命中示例包括：国旗、历史人物特写、阅兵队列、大炮、坦克/装甲车、群众集会、爆炸烟雾、战场士兵、战斗场景和山地行军队伍。结论是：对当前样片，镜头代表帧加中文 CLIP 的 Top-3 足以作为高召回入口；但 Top-1 仍然会把相似环境当成受伤或持枪，因此不得使用“最高相似度 = 已检测到内容”的产品逻辑。

首期界面应默认展示每个视觉查询的 Top-3（或条目配置的 Top-K）候选，并支持审核员快速排除同类误报；只有接入经专项验证的专用模型、并满足库条目的确认条件后，才允许将视觉结果提升为确认级证据。

### 15.2 OCR、ASR、视觉语义的实际归并

以《**中国人民的胜利**》104.57–138 秒的军用装备片段为例，临时内容库定义三个子条目：`firearm`、`artillery`、`armored_vehicle`。每个条目分别允许 OCR 精确文字、ASR 精确/变体文字以及中文 CLIP 视觉候选。

原始 OCR 在该窗口检测到连续重复的“自动步枪”“大炮”“装甲车”“坦克”等文字；ASR 检测到“自动部枪”“打炮”“装甲车”“坦克”等结果；中文 CLIP 分别召回步枪士兵（104.57 秒）、大炮（126.65 秒）和装甲车辆/坦克（128.07、132.67 秒）关键帧。

| 处理阶段 | 结果 | 说明 |
|---|---:|---|
| 按库条目匹配的原始证据 | 32 条 | 包含 OCR 连续重复帧、ASR 分段和视觉 Top-K 候选。 |
| 同来源连续重复折叠后 | 18 条 | 相同来源、相同条目、相邻 1.1 秒内的重复文字合并；保留起止时间和原始证据。 |
| 跨来源归并后 | 1 张父级复核卡 | 104.57–138 秒；三个子问题分别保留，而不错误地合并为一个“武器标签”。 |

最终复核卡包含 `firearm`、`artillery`、`armored_vehicle` 三个子问题，每个都有 OCR、ASR 与中文视觉检索来源。对 ASR，先做简繁标准化，再将“自动部枪”作为库中显式配置的低置信变体命中；它增加召回，但不能改写高置信 OCR 原文“自动步枪”。

这验证了首期应采用**父级复核上下文 + 子条目证据**的数据模型：一张卡减少审核员在同一连续片段中反复跳转；子条目、来源、原文和置信等级仍独立保存，避免把“画面附近有装备文字”误写成某一种装备已经被视觉确认。

## 16. 1960–1980 年代真人片源、人物库与向量检索验证

### 16.1 人物库不是“给一张脸就自动可靠”：跨镜头试验

在 1981 年新闻纪录片中，从约 60 秒的清晰讲台近景建立一个**受控人物库测试对象 A**参考图，并故意将 55–85 秒的参考镜头从检索评价候选中排除。以现有 YuNet + SFace 流程按约 0.5 秒抽样，结果如下：

| 归并事件 | 最高相似度 | 模型状态 | 人工查看 |
|---|---:|---|---|
| 57.06–60.06 秒，讲台近景 | 0.9058 | 确认 | 参考镜头，验证检测与特征提取。 |
| 65.57–68.57 秒，讲台远景 | 0.6676 | 确认 | 同一人物，尺度显著变小仍被召回。 |
| 237.74–241.24 秒，户外侧面特写 | 0.5195 | 待复核 | 同一人物；侧脸和光照变化使分数低于当前自动确认阈值。 |
| 90.09、178.68、200.70 秒等人群/会场单帧 | 0.4376–0.4556 | 待复核 | 有同一人物和低质/小脸混杂，不能仅凭单帧升级为确认。 |

同一轮中也以《龙城十日》约 285 秒的可检测演员脸作为受控参考做了暗光剧情片试验。只稳定确认到参考镜头附近；跨镜头候选多为孤立低分且人物较小、遮挡严重，不能可靠归入该演员。因此，首期不能声称“任意电影演员全片自动找人”：人物库条目至少应有多张清晰正/侧脸参考图、质量门槛、任务内多帧支持和人工复核队列；暗光或运动剧情片应降级为候选召回。

### 16.2 Faiss 索引验证：解决规模，不替代身份判断

对上述 1981 年样本每秒抽一帧，检测并写入 2,285 条 128 维、L2 归一化的人脸特征，同时保存 `媒资版本 / 时间戳 / 人脸框 / 特征模型版本 / 原始关键帧` 映射。用受控对象 A 的 60 秒参考图查询 `Faiss IndexFlatIP`，排除 55–85 秒参考窗口后，排名前两项是 238.24 秒（0.5047）和 239.24 秒（0.4649）的户外侧面镜头；人工查看均为同一人物。前列还包含会场小脸和至少一个不确定候选。

该实验验证了 Faiss 能按元数据回到可复核的原始画面，也说明它只是近邻索引：`IndexFlatIP` 是精确检索，**没有提高 SFace 的身份区分能力**。产品接入时应把人脸模型相似度、质量分、参考图数量、时间连续性和人工反馈用于决策；当库规模确实增长后，再以固定召回率目标评测 IVF/HNSW 等近似索引，而不能因“换了 Faiss”下调确认门槛。

### 16.3 1981 年彩色实拍中的 PySceneDetect 与 Chinese-CLIP

以 `ContentDetector(threshold=27, min_scene_len=60 帧)` 切分 304 秒样片，得到 68 个镜头代表帧，耗时 2.43 秒；相对 1 fps 的 304 帧基础抽样减少约 78%。在这些代表帧上运行 Chinese-CLIP RN50：

| 视觉查询 | 代表帧检索结果 | 结论 |
|---|---|---|
| `讲台上演讲的男性` | Top-3 均为讲台演讲画面或极近似构图 | 适合作为演讲/讲话类候选入口。 |
| `会议中的人群` | Top-1 为会场人群，后续候选也为会议或观众场景 | 对显著人群结构有效。 |
| `室外旗帜和仪式` | Top-1 为约 23.65 秒的多旗户外画面 | 对明确的旗帜与仪式构图有效。 |
| `骑马队伍` | 实际约 270 秒的骑马镜头未排入代表帧 Top-3 | 失败样本：一个镜头只取一张代表帧会漏掉镜头内部短暂事件，且该开放词表模型对马匹/队伍区分不稳。 |

对 250–280 秒窗口改为每秒抽样后，`骑马的仪仗队`把 269 秒骑马画面排到第 7，仍不适合确认。这一反例决定了两条产品规则：一是任何视觉语义命中都要触发命中镜头及邻域的加密抽帧；二是对“马匹、武器、裸露、斗殴”等需明确对象或时序事实的库条目，开放词表检索只能扩大候选，必须另行以经标注验证的专用检测/动作模型决定是否可自动确认。

### 16.4 当前技术结论

1. **可进入下一阶段联调：** PySceneDetect 的按片源预设切分、OCR/ASR/人脸/Chinese-CLIP 的并行候选召回、证据映射和父卡归并；小规模向量索引可先使用 Faiss 精确索引。
2. **必须作为复核而非结论：** 单参考人脸、Chinese-CLIP 任意 Top-1、暗光剧情片人脸候选、通用 YOLO 的物体标签。
3. **暂不投入高 ROI 不明的实现：** 全量部署 MMAction2，或为未有专项标注集的内容类别预训练动作识别器。先用本系统积累“库条目—候选—人工确认/排除”的评测数据；只有某类误报/漏报确实构成审核瓶颈时，再对该类做专项模型验证。

## 17. 著名演员人物库的盲测预实验

本节启动的是“先保准、后扩召”的人物库盲测预实验。它与“从同一张参考脸找相邻帧”的演示不同：参考窗口、测试窗口和人工标签窗口分离；模型仅得到人物库参考图，不能读取标签。正式指标仍需由第二位审核人员在不知道模型结果的条件下复核，本轮先验证实验设计、参考库质量和候选卡行为。

### 17.1 测试对象与材料依据

选择 [《再见阿郎》](https://commons.wikimedia.org/wiki/File:%E5%86%8D%E8%A6%8B%E9%98%BF%E9%83%8E_%281970%E5%B9%B4%E9%9B%BB%E5%BD%B1%29.webm) 的主演 **柯俊雄** 作为首个受控演员对象。影片来源页面标示了可用状态；公开影视资料与文化部出版资料均将柯俊雄对应为角色“阿郎”，张美瑶对应为“桂枝”。这是演员姓名、角色和测试画面能够相互核对的前提。

另找到一张 [1968 年柯俊雄档案照](https://commons.wikimedia.org/wiki/File:1968%E5%B9%B4%E5%BD%B1%E6%98%9F%E6%9F%AF%E4%BF%8A%E9%9B%84%E5%9C%A8%E9%A6%AC%E7%A5%96%E6%9C%8D%E5%BD%B9.jpg)：文件说明明确其为左起第三位的柯俊雄，并标示为权利人作出的公共领域标记。该图用于模拟“人物库从影片外部提供参考图”的真实情况。

### 17.2 时间隔离的检索预实验

| 项目 | 设置 |
|---|---|
| 开发/参考窗口 | 10:10–10:35，5 张清晰正脸或侧脸；不参与测试。 |
| 测试窗口 | 11:00–22:00，按 2 秒抽样；测试前按每 5 秒联系人表人工标出可见窗口。 |
| 检索方式 | YuNet 检脸、SFace 128 维特征；对参考图集取最大余弦相似度。 |
| 候选门槛 | 0.45，仅为此次预实验的候选门槛，不是产品全局阈值。 |
| 归并规则 | 相邻 4 秒内的命中合并为一张人物复核卡，保留最佳帧和所有原始命中。 |

在 660 秒测试窗口中得到 26 条原始人脸候选，归并为 12 张复核卡，候选条目减少约 54%。其中 11:10–12:34 和 20:48–21:46 的多张卡包含清晰的主演跨镜头画面；16–18 分钟的群像场景还出现相似度接近阈值的候选。这符合“保准不保召”的处理方式：只有“多帧支持且分数足够高”的卡可升为高优先级，其余仍交人工，而不是因单帧相似就确认演员出现。

以 `分数 >= 0.55 且至少 2 个采样帧支持` 作临时高优先级条件，12 张卡中只有 4 张进入高优先级。一个清晰目标卡的最高分为 0.548，恰好落在门槛外，说明单一数值门槛很脆弱；产品需要将参考图质量、清晰度、正/侧脸姿态和连续帧支持一起记录，而不能只存一个相似度阈值。

### 17.3 外部人物库参考图的反例

将同一演员的 1968 年单张档案照作为唯一参考，以相同测试窗口检索。该照片为黑白群像、目标脸较小，且与 1970 年彩色剧情片的妆造、姿态和成像条件不同。对已知主演清晰镜头，最高相似度仅约 0.322，未达到 0.45 的候选门槛。

这不是“演员不在画面中”，而是一个有价值的失败结果：**单张外部宣传/档案照不能构成可生产使用的人物库。** 人物库条目应至少保存：身份来源、授权/使用范围、参考图版本、拍摄年代、外观阶段、正侧脸、清晰度、特征模型版本和人工验收状态。针对赵本山、朱时茂等高频演员，也必须按此规则收集多张有权使用的参考图与独立测试媒资；不能从搜索结果随意抓取图片或表演片段。

### 17.4 开源词表与内容库的接入边界

开源敏感词项目可作为**种子词和匹配引擎**，不是广电审核规则库。初步可评估 [houbb/sensitive-word](https://github.com/houbb/sensitive-word) 与 [ToolGood.Words](https://github.com/toolgood/ToolGood.Words)：两者上游均标示 Apache-2.0，支持简繁转换、变体或高性能多词匹配。接入前仍需逐条检查词表来源、更新时间、语义分类和许可；开源仓库的代码许可证不自动证明每个词条适用于业务政策。

正确做法是将外部词条导入隔离的“候选种子区”，由内容运营/合规人员映射为内部库条目，例如 `text.drug_term`、`text.violence_term`、`text.explicit_term`。每个内部条目再声明同义词、变体、适用证据源、阈值、确认条件和版本。OCR/ASR 命中外部种子词只能生成候选，不直接写为风险结论。
